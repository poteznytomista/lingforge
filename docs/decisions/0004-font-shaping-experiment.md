## Library boundary and compatibility review

Use a separate filesystem/UI-independent `lingforge-font` crate depending on core domain types. Storage depends only on the profile model; the desktop host calls the compiler on its blocking worker. No subprocess, Python runtime, HarfBuzz system package, font installation privilege, shell permission or network access is required for application operation.

The APIs inspected include FontBuilder, cmap mappings, glyf/loca construction, glyph rounding, font metric/name tables, FEA Compiler/GlyphMap/source resolver, and rustybuzz buffers. Use a restricted in-memory FEA resolver: arbitrary includes and user-authored code are unnecessary and must remain unavailable.

## Shaping versus layout

HarfBuzz is responsible for glyph substitution/positioning, while the application retains original character identities and cluster associations. We use its existing Rust port, rather than implementing a second shaper. [HarfBuzz's cluster contract](https://harfbuzz.github.io/working-with-harfbuzz-clusters.html) informs source-index reporting; it does not provide a complete editing/caret model.

The reference run is deliberately generic DFLT with explicit direction. FontFace offers a separate platform-rendering observation from the same generated bytes. Matching their output, visual selection and native IME behavior requires real fixtures; neither a font parser accepting bytes nor synthetic component events establishes that compatibility.

Mixed-direction layout needs itemization, [Unicode bidi processing](https://www.unicode.org/reports/tr9/), line breaking, grapheme segmentation and visual/logical cursor mapping. PUA values cannot encode all those semantics. No bidi engine or hidden override is added to documents. The lab's visible single-run direction choice is not an automatic paragraph direction policy.

Context, ligature and one-class mark-to-base experiments use a generated subset of the [OpenType Feature File specification](https://adobe-type-tools.github.io/afdko/OpenTypeFeatureFileSpecification.html). Stacked marks, mark-to-ligature attachment, cursive joining, script-specific reordering and vertical layout need separate data/fixtures. Embedding choices map to [OpenType fsType metadata](https://learn.microsoft.com/en-us/typography/opentype/spec/os2#fstype); they are authored permissions, not an inferred license.

## Alternatives and unresolved gates

External FontForge/fontTools/fontmake could provide broader authoring pipelines, but would introduce user-installed tools or sidecars before their need is demonstrated. A bespoke binary font writer would duplicate established encoding work. Direct native HarfBuzz is a future option if the Rust port fails compatibility/performance fixtures; no such failure has been observed because execution has not occurred.

The current cubic-to-quadratic adapter has explicit precision/resource limits. Independent SVG path painting cannot always be collapsed into one nonzero TrueType outline without boolean union, so the prototype rejects that case instead of silently altering shapes. A production compiler may use established outline conversion/union facilities after evidence and dependency review.

PDF export is conditional on dependable font embedding, subsetting, text extraction, accessibility and actual native/external application checks. It stays deferred. The individual writing-system evaluation and required platform evidence are recorded in [the Part 8 protocol](../experiments/part-8-font-checks.md). No richer-script capability is production-supported yet.

## Execution correction — 2026-11-17

The downloaded official fea-rs 1.0.0 Cargo manifest requires write-fonts 0.52.0, not the 0.55.0 stated in the initial source-only review. Compilation demonstrated incompatible table types from two Fontations versions. The direct write-fonts pin is now 0.52.0; its published manifest declares Rust 1.85 and Kurbo 0.13 compatibility. See [the live validation record](../GUIDE.md). Earlier source-only assertions are not execution evidence.
